# Снятие каталога вызовов

Цель — собрать `actions.draft.json` (черновик с реальными `action`/`endpoint` твоего портала),
из которого затем делается `actions.json`. Два способа: **A — авто-запись расширением** (проще,
без DevTools) и **B — HAR вручную**.

---

## Вариант A — авто-запись расширением (рекомендуется)

Расширение в capture-сборке перехватывает все API-вызовы страницы и стримит их локальному
рекордеру, который пишет `actions.draft.json` и показывает покрытие Триады в реальном времени.

1. Собери **capture**-сборку расширения и перезагрузи его:
   ```bash
   bun run build:ext:capture
   ```
   `chrome://extensions` → у расширения нажми «Обновить» (или Load unpacked → `extension/dev/`).
2. Запусти рекордер (использует тот же `.env`):
   ```bash
   bun run capture
   ```
   Он слушает мост и пишет `actions.draft.json`. Оставь его запущенным.
3. Открой вкладку портала — внизу справа появится красный бейдж **● REC**. Прокликай по каждому
   домену Триады: задачи (список + одна задача), проекты (список групп + внутрь группы),
   чаты (мессенджер + диалог + прокрутка истории).
4. Следи за терминалом рекордера: строки `+ ajax POST tasks.task.list` — новые пойманные вызовы;
   `still missing: projects` — домен ещё не покрыт. Когда увидишь `✓ all triad domains captured` —
   нажми **Ctrl-C**. `actions.draft.json` готов.
5. **Верни обычную сборку** (важно): capture-сборка вешает хук на `fetch` и рисует бейдж —
   для повседневной работы агента это не нужно.
   ```bash
   bun run build:ext
   ```
   И снова «Обновить» расширение.

Дальше → раздел «Собрать `actions.json`» ниже.

---

## Вариант B — HAR вручную

1. Открой вкладку своего Bitrix24, залогинься.
2. DevTools → Network → включи "Preserve log" (фильтр НЕ ставь — ловим всё).
3. Прокликай те же действия по Триаде (см. пункт A.3).
4. ПКМ по списку → "Save all as HAR with content" → `captured.har` (в корень проекта).
5. `bun run catalog:draft` → создаст `actions.draft.json` в корне (скрипт всегда работает из корня проекта).
   Для другого имени/пути HAR: `bun run catalog <путь.har> > actions.draft.json`.
6. Прочитай предупреждения в stderr: если по какому-то домену "nothing captured" —
   вернись в браузер и прокликай его ещё раз.

---

## Собрать `actions.json`

Из `actions.draft.json` выбери нужные вызовы и присвой понятные ключи, которые ждут инструменты:
`tasks.list`, `task.get`, `projects.list`, `chats.recent`, `chat.messages`
(можно меньше — недостающие инструменты просто не зарегистрируются). Поля
`endpoint`/`action`/`method` оставь как в черновике; `transport`/`sampleParams` можно не переносить.

Мутирующие вызовы (`…add`/`…update`/`…delete`/…) допустимы — загрузчик каталога их больше
не отклоняет; allowlist (сам факт присутствия записи в `actions.json`) — единственная граница.

Примечание: HAR-парсер (вариант B) читает параметры из тела POST, а не из query-строки URL —
GET-вызовы с params/sessid в query захватятся с пустыми params (для POST-based Триады не проблема).
Авто-запись (вариант A) берёт тело fetch/XHR и отсекает статику по расширению файла.

## Транспорт записи каталога

**`bodyType` — как мост кодирует тело** (черновик из capture проставляет его автоматически):

- **`"form"`** (по умолчанию) — `application/x-www-form-urlencoded`; вложенность кодируется PHP-стилем
  (`filter[STATUS]=2`, `select[0]=ID`). Объект в `params` рекурсивно разворачивается в такие ключи.
  Классические `tasks.task.*`, мессенджер `im.v2.*`, REST — всё это форма.
- **`"json"`** — тело уходит как `JSON.stringify(params)` с `Content-Type: application/json`; `params`
  сохраняет вложенную структуру как есть. Так работают **`tasks.v2.*`** (напр. `tasks.v2.Task.get` ждёт
  `{"task":{"id":N}}`) и `ui.entityselector.*`.

**`responseType` — как разбирается ответ:**

- **`"json"`** (по умолчанию) — ответ разбирается как JSON и проходит через конверт (`docs/api-notes.md` §2).
- **`"text"`** — сырой ответ `{ contentType, text }` без разбора: для серверного HTML (side-slider'ы —
  детали звонка, легаси-комментарии задач). Ошибкой считается только HTTP ≥ 400 или пустое тело, поэтому
  редирект на логин приедет как «успешный» HTML — распознавать его должен разбирающий инструмент
  (так делает `bitrix_call_detail`: нет `data-call-id` → внятная ошибка).
- **`"binary"`** — тело не возвращается, а **стримится на диск**: расширение читает его как `ArrayBuffer`
  и шлёт по WS чанками base64 по 1 МиБ (`binary-begin` → `binary-chunk`×N → обычный `result`), daemon
  пишет их в файл. Вызывающему приходит только `{ path, bytes, contentType, fileName }`, потолок — 512 МБ.
  Признак реальной загрузки — `Content-Disposition: attachment`; HTML без него считается страницей логина,
  вызов падает и частичный файл не остаётся. Имя берётся из `Content-Disposition`, поэтому без `savePath`
  тело сначала пишется во временный `.download-*.part`, а затем переименовывается.

**Path-параметры в `endpoint`.** `endpoint` может содержать плейсхолдеры `{имя}` — значение берётся из
`params` и подставляется в URL (а из тела/query исключается): `"/call/detail/{callId}"` +
`params: { callId: 4242 }` → `GET /call/detail/4242`. Нет значения — вызов падает с внятной ошибкой,
а не уходит с дырой в URL.

**CSRF / sessid.** Мост всегда шлёт заголовок **`X-Bitrix-Csrf-Token: <sessid>`** (свежий
`BX.bitrix_sessid()`). Form-тела дополнительно несут `sessid` полем в теле (legacy REST это требует);
JSON-тела — только в заголовке. Ответ `invalid_csrf`/`invalid_authentication` = сессия протухла.

## Как расширить (новый домен: календарь, диск, CRM, …)

> Сперва проверь, задокументирован ли метод в [`apidocs.bitrix24.com`](https://apidocs.bitrix24.com)
> (context7: `/bitrix24/b24restdocs`). Для публичных `*.list`/`*.get` там готовые поля, фильтры и
> пагинация — реверс тогда нужен лишь чтобы подтвердить транспорт и конверт ответа. Для внутренних
> `im.v2.*`/`tasks.v2.*`/UI-методов доков нет — только реверс.

1. Сними реальные вызовы (варианты A/B выше). Черновик `actions.draft.json` накапливает **все уникальные
   комбинации параметров** на экшен и проставляет `bodyType` автоматически.
2. Определи транспорт (раздел выше): если черновик показал `"bodyType": "json"` — перенеси его в запись.
3. Добавь запись в `actions.json` (может быть мутирующей — каталог это допускает).
4. Если удобно — оберни в типизированный инструмент в `src/tools/register.ts` (обёртка регистрируется
   только если её `catalogName` есть в каталоге) и опиши метод в `docs/api-notes.md`.
5. **`bun run sync:runtime`** — доставь изменения живому daemon: пересобрать бандл, скопировать
   репо-`actions.json` в `~/.bitrix24-mcp-bridge/actions.json` и погасить daemon. Без этого агент новых
   имён/инструментов не увидит (daemon читает runtime-папку, не репо).

**Новую запись клади и в `actions.example.json`** — именно он едет в npm-пакет и раздаётся установленным
мостам: при старте недостающие записи дописываются в пользовательский `actions.json` автоматически
(удалённые пользователем — не воскрешаются, см. `src/catalog/sync.ts`). Запись только в локальном
`actions.json` останется вашей личной.

## Кандидат на реверс: легаси-комментарии задачи (HTML-поддомен)

У задач два независимых фида обсуждения: **im.v2-чат** (структурный JSON, читается уже сейчас) и
**форумные легаси-комментарии**, которые рендерятся как HTML в side-slider'е и мостом пока не поддержаны.

Первая страница — GET HTML-страницы iframe (сервер тут же минтит подпись):

```
GET /task/comments/<taskId>/?IFRAME=Y&IFRAME_TYPE=SIDE_SLIDER   → HTML (комментарии + signedParameters)
```

Листание — POST компонентного ajax (форма, отдаёт HTML-фрагмент):

```
POST /bitrix/services/main/ajax.php?mode=class&c=bitrix:forum.comments&action=navigateComment
form: AJAX_POST=Y, ENTITY_XML_ID=TASK_<taskId>, taskId=<taskId>, MODE=LIST,
      FILTER[<ID]=<курсор: id, ДО которого грузить старые>, PAGEN_1=1,
      signedParameters=<подписанный blob>, IFRAME=Y, IFRAME_TYPE=SIDE_SLIDER
headers: bx-ajax: true, x-bitrix-site-id: s1 (плюс обычный X-Bitrix-Csrf-Token)
```

`signedParameters` — base64 PHP-массива + HMAC-подпись сервера (`FORUM_ID, ENTITY_TYPE=TK,
ENTITY_ID=<taskId>, …`); подделать нельзя, берётся из HTML первой страницы.

Что осталось сделать: запись каталога `"/task/comments/{taskId}/"` с `responseType: "text"` даст ПЕРВУЮ
страницу уже сейчас; для листания нужен механизм кастомных заголовков (`bx-ajax`, `x-bitrix-site-id`)
пер-запись и прокидывание выпарсенного `signedParameters` в `navigateComment`.
